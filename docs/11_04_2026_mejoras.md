## Lo que baja la nota ⚠️

### 1. Sin documentación de API (OpenAPI/Swagger)
**Impacto: ALTO — afecta directamente a la app móvil**

La app móvil tiene 418 archivos Kotlin consumiendo la API. No existe ningún contrato formal documentado. Si el backend cambia un campo JSON (renombra, cambia tipo, elimina), la app móvil silenciosamente falla en producción sin que haya ningún mecanismo que lo detecte antes.

```
Riesgo: cambias ContainerResponse en backend → la móvil crashea o recibe null
Sin Swagger: nadie lo detecta hasta que un usuario reporta el bug
```

**Solución:** Generar OpenAPI desde el código con `dedoc/scramble` (Laravel-native):
```bash
composer require dedoc/scramble
```
Accesible en `/docs/api`. Los DTOs/Resources de Laravel generan el schema automáticamente.

---

### 2. Sin excepciones custom estructuradas
**Impacto: ALTO — la móvil recibe errores genéricos de Laravel**

Cuando algo falla en el backend, la app móvil recibe un `500 Internal Server Error` sin contexto útil, o un mensaje de validación en formato inconsistente.

**Estado actual:**
```json
{ "message": "Server Error" }
```

**Estado deseable (para móvil):**
```json
{
  "error": "INSUFFICIENT_STOCK",
  "message": "Stock insuficiente para el contenedor",
  "context": { "available": 150, "requested": 200 }
}
```

**Solución:** Crear `app/Exceptions/` con excepciones de dominio y un Handler centralizado:
```php
// app/Exceptions/InsufficientStockException.php
// app/Exceptions/ContainerCapacityException.php
// app/Exceptions/UnauthorizedRoleException.php
// app/Exceptions/Handler.php → render() con JSON estructurado
```

---

### 3. Servicios demasiado grandes (violación SRP)
**Impacto: MEDIO — dificulta mantenimiento y debugging**

| Servicio | Líneas | Problema |
|----------|--------|---------|
| `ContainerStockService` | ~1016 | Transformación + BD + cálculos + historial |
| `VerifactuService` | ~706 | Generación XML + firma + envío AEAT + logging |
| `WineContainerStockService` | ~700 | Similar al anterior |

Cuando la móvil llama a un endpoint que usa `ContainerStockService` y falla, el stack trace recorre 1000 líneas antes de localizar el problema.

**Solución gradual:** Extraer responsabilidades en clases más pequeñas:
```
ContainerStockService
  → ContainerStockCalculator   (cálculos puros, sin BD)
  → ContainerHistoryRecorder   (solo escritura de historial)
  → ContainerStockValidator    (validaciones previas)
```

---

### 4. Componentes Livewire con lógica excesiva
**Impacto: MEDIO — deuda técnica web, no afecta móvil directamente**

Varios componentes Livewire superan las 700 líneas mezclando UI, validación y lógica de negocio:
- `VisualDashboard`: 811 líneas
- `ProductSale`: 742 líneas
- Varios `CreateXxx` / `EditXxx` del cuaderno digital

La app móvil no usa Livewire, pero si la lógica de negocio está enterrada en un componente en lugar de en un Service, ese código no es reutilizable desde los controladores API.

**Solución:** Mover lógica compleja de Livewire a Services existentes o nuevos. El componente solo debería orquestar, no calcular.

---

### 5. Sin manejo centralizado de excepciones API
**Impacto: MEDIO**

Laravel tiene `app/Exceptions/Handler.php` por defecto. El proyecto usa el default sin customizar. Esto significa:

- En `debug=true` (desarrollo): la móvil recibe stack traces completos con rutas del servidor
- En `debug=false` (producción): la móvil recibe `{"message": "Server Error"}` sin más
- Las excepciones de validación tienen formato diferente a las excepciones de negocio

**Solución:**
```php
// app/Exceptions/Handler.php
public function render($request, Throwable $e): Response
{
    if ($request->is('api/*')) {
        return $this->renderApiException($request, $e);
    }
    return parent::render($request, $e);
}
```

---

### 6. Lógica de rol en controladores en lugar de Policies
**Impacto: BAJO**

Algunas rutas verifican `$user->role !== 'admin'` directamente en el controlador en lugar de delegar a una Policy. Inconsistente y difícil de mantener si los roles evolucionan.
